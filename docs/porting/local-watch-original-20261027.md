# 本地观战原件与取消证明（2026-10-27）

状态：候选源码与测试已逐文件核对 SHA-256 后接入独立 Java 工作树，尚未编译或执行。本节不代表全量迁移完成。

## 基线事实与问题

实现事实核对固定 C++/Go 提交 `92952c84b00f5dd45bf3b05ed4d08b9d7b5bd1b5` 的
`go/match/internal/logic/spectate.go`、`watchbattlelogic.go`。该基线本地观战已生成规范 UUID、25 秒准入截止、固定 battle 实例，
完整 Add 原件先随标记保存再发出。相同战斗的重看也先取消旧操作，否则新 UUID 无法进入仍由旧 UUID 占用的观众席。

Java 原有本地路径只发战斗号、角色、路由与名字，缺少 battle 操作账本必需的三个字段；旧标记只存 battle 与 nonce，
后续 Remove 无法携带原操作。全球 SQL 路径已有自己的观战许可和账本，本次仅修本地路径及共用直拨接口。

## Java 实现

- `LocalObserverOperation` 为不可变 record，保存完整 `BattlePlacement` 与 protobuf Add。版本化 Base64 标记有 65,536 字符上限，
  解析检查身份、规范 UUID、端点、固定实例与观众路由，重编码验证规范串，保留 protobuf 未知字段。
- 新操作先按原子存储接口抢标记，再发 Add；成功应答带操作 UUID。准入截止取同次落点快照的 Redis 时间加 25 秒。
- 取消仅接受原件，不再提供无操作号的长参数删除入口。固定地址、实例、角色、战斗、操作号、准入截止都从原件取得。
  `cancelled=true`、原 UUID、原实例全部吻合才视为取消成功。空回包、错误回包、超时、未送达、目录判死都不当作取消证明。
- 同场重看、换场和随机重看均先取消旧原件，确认后按旧字符串 compare-delete，再开始新操作。
- Add 未知或成功后的并发排队复查命中时，用独立 3 秒预算补发原件取消。只有取消正证明回调才异步 compare-delete；
  迟到回调不能删后来操作的标记。取消未知保留恢复原件。
- 开局清退不重读后来可能消失或变更的落点；它按标记原件寻址，确认后删标记。未知或损坏的 `observer-` 版本族保留，
  已无法通过当前账本的旧格式按原值清理。日志不打印完整原件标记。
- 新增固定指标原因 `watch_outcome_unknown`，无玩家号等高基数标签。

这不是逐句翻译 Go：Java 保留原端点，采用注入的协作者、不可变值类型、封闭结果类型与明确取消证明，
对无证明结果比固定 Go 基线更保守。没有新增依赖、传输库、同步契约改动或 C++ 改动。

## 仍有的边界

本地链仍是 Redis TTL、分离存储复查与尽力开局清退，取消失败不阻断既有 gather；
这不构成观战与参战的跨存储强事务互斥，也不证明多副本、TiDB、Redis 集群或双区故障场景通过。
未知取消保留标记至后续恢复或 TTL；没有新增持久恢复队列或自动重试调度。
