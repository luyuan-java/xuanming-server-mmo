## 不移植（及原因）

- 导表主流程与客户端各语言表产物：表数据是两版共享的契约，只在 mmorpg 导出一次，Java 消费同一份产物。
- 消息号 / 事件号发号：契约在 mmorpg 定，Java 只同步。
- C++ ECS 组件生成、C++/Go 内部 proto 产物、仓库卫生补丁：Java 没有对应物。
- 战斗美术程序化生成（battle_art_gen）：客户端资源工具，与服务端无关。
- 存储落点多库路由 / 在线搬库、跨区 KV 代理：mmorpg 的 TiDB 分库方案；Java 版存储方案另行设计，到合服 / 扩容批次时再定。
- 会话级消息签名密钥、遗留 gate RPC、心跳：mmorpg 未启用或已废弃。
- 存档写库进程 db 的多实例（重试收据按实例归属 + 租约回收，基线 `be6b4ab1d`，2026-10-12 登记）：Java 不经 Kafka 落库（scene 持 owner_epoch 同步写回 MySQL），没有重试收据队列与 db 进程；
  将来若给 db-task-retry-dlq 补持久化的重写队列，按「收据按实例归属 + 租约回收 + 停机归还」设计。
- 基线 CPP-3 的改派待确认表（2026-10-12 登记）：Java 5.5 走 5.2 交出事务改派、交出前失败原地留下，不存在「先销毁实体再改派」的哑会话，失败出口的差异作为有意差异登记（scene-drain-spec 文首）。
