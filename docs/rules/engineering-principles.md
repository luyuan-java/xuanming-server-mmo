# 工程设计与编码原则（Java 版）

> 对应根索引 [AGENTS.md](../../AGENTS.md)，移植自 C++/Go 服务端仓 `docs/rules/engineering-principles.md` 并结合 Java 21 / Spring Boot / Netty 服务端实践。适用于新增、修改、重构与评审。

原则冲突时按以下顺序取舍：

`正确性 / 安全 / 数据强一致性 / 向后兼容 > 简单 / 可读 / 与仓库一致 > 可维护 / 可测试 > 有数据支撑的性能 > 假想扩展`

偏离本文件原则必须有当前需求或证据支撑，并在注释、设计文档或交付说明中记录原因与代价。

## 1. 模块与职责（SOLID 与设计模式）

- **单一职责（SRP）**：一个类 / 模块只对一种变化原因负责；协议适配、业务策略、持久化存储与副作用严格分离。
- **高内聚、低耦合与显式依赖**：相关状态与行为就近收口，依赖单向不成环；统一走 Spring 构造器注入或显式参数传值，不引入静态可变全局单例。
- **开闭（OCP）/ 里氏替换（LSP）/ 接口隔离（ISP）/ 依赖倒置（DIP）**：在已确认的多变体或外部隔离接缝处定义接口，拒绝没有隔离价值的连续透传层与万能 `Manager`。
- **组合优于继承**：优先组合可替换组件构建能力，继承仅用于稳定 is-a 契约。
- **23 种经典设计模式的使用原则**：如果某个结构确实适合用 GoF 23 种设计模式（如策略、状态、工厂、适配器、责任链、观察者、模板方法、命令等）来解耦、消除巨型 `if/switch` 分支或隔离明确变化轴，**主动采用或向程序建议采用，并明确告诉程序为什么用这个模式**（解决了什么具体耦合/扩展/维护痛点、替代了什么更糟的写法）；严禁为了套模式而无故堆砌抽象层。
- **系统 / 模块间消息通信（Actor 隔离，强制）**：
  - **状态私有**：每个业务系统 / 模块（如场景、战斗、背包、社交、公会等）独占自身可变状态，禁止跨模块直接读写内部字段，禁止在消息中传递可变对象引用（避免“假隔离”与并发脏读写）。
  - **不可变消息驱动**：跨系统、跨线程（如 Netty EventLoop ↔ 场景逻辑线程）、跨进程交互一律通过显式定义的**不可变消息**（Mailbox 投递 / 领域事件 / RPC / Kafka）通信，严禁跨模块直接同步调用内部实现，也禁止通过全局单例、静态变量或共享缓存绕过消息通道。
  - **串行消费与防错**：每个 Actor / 所属线程串行消费消息队列，靠消息所有权与幂等键保证一致性，而非跨模块加锁；跨模块消息契约须显式处理超时、乱序与重复投递。
  - **作用边界清晰（防过度设计）**：上述约束仅适用于**系统 / 模块之间与跨线程、跨进程边界**；单个模块内部仍用正常直接方法调用，**严禁把模块内部普通函数或内聚逻辑无意义地拆成消息**。

## 2. 简单、标准、可读与开源库选型

- **KISS / YAGNI / DRY**：未上线阶段玩家数据可清空，按最标准方案直接落地与重构，不堆砌历史兼容包袱；一条业务真相只保留一个权威源。
- **命名第一原则**：详见 [naming-and-boundaries.md](naming-and-boundaries.md)——所有命名必须清晰易懂、语义完全准确并标明单位。
- **第三方开源库选型（强制：先标准库，再找同语言 GitHub 高 Star，交由程序决策）**：
  1. **优先标准库**：先用 JDK 21 标准库与 Spring Boot 官方组件（视为事实标准）；标准库能解决的不引入第三方依赖。
  2. **按当前开发功能的语言去 GitHub 找同语言库**：标准库没有时，开发 Java 功能就去 GitHub 找 **Java 生态**同类头部高 Star 且活跃安全的成熟库（Star 门槛按该语言生态体量浮动——Java 生态体量大，通用库优先参考 ≥ 2 万 Star、**同类取 Star 最高**；垂直细分组件按 Java 同类头部与维护质量综合评估）。
  3. **交由程序决定并说明原因**：不擅自默默引入新依赖，把候选库与“是否自研”交给程序决定，并清楚说明为什么（标准库/Spring 现有能力的不足、该库解决什么核心问题、引入代价与安全风险），确认后登记进 `docs/design/tech-stack.md`；**安全 > Star**（例：严禁引入 `fastjson 1.x` 等存在历史高危漏洞的库）。

## 3. 正确性、一致性与线程/连接生命周期

- **Fail-closed 与提交点原子性**：不可信输入在入口严格校验；玩家资产、权限与归属写回必须带 `owner_epoch` 围栏，禁止吞错或静默降级；发现已知问题与隐患当场闭环修复，不留“等压测/以后再修”的债务。
- **线程所有权与不乱开线程**：
  - scene 场景状态只在场景逻辑线程读写；gate 会话状态只在该连接的 Netty EventLoop 上读写；阻塞 I/O（MySQL / Redis）严禁在 Netty I/O 线程或场景逻辑线程上执行，结果投递回所属线程；
  - **默认不私自新开独立线程/线程池**：除非压测数据证实瓶颈确需新开线程（例如评估新增独立 Kafka consumer 消费线程），且**必须先与程序/负责人确认并说明原因与压测依据**。
- **连接与回调生命周期**：长期持有的 Netty `Channel` 引用在关闭后必须及时清掉；异步回调回到逻辑线程时，第一步先校验目标玩家/连接/会话代次是否仍有效，已断线或已切会话直接丢弃。
- **面向接口测试与全链路核对**：优先测试可观察契约，单测不依赖执行顺序、真实墙钟或外部残留状态；修改任何规则或契约时排查所有读写/迁移/恢复/清理路径。

## 4. 实例与布局分层（数据层 / 显示层，强制）

一条记录只回答一个问题：**「它是什么」**，还是**「它摆在哪」**（适用于背包/仓库/装备、宠物出战、队伍站位、技能栏、时装坐骑、邮件附件等）：
- **实例层只描述实体**：身份（`guid`）、模板（`config_id`）、数量、状态、时间戳，不混入 `pos` / `slot` / `index` / 排序等摆放字段；
- **布局层只描述排列**：容量、槽位、占位与整理策略，布局层源码不得反查配置表或混入领域实体；
- **「是什么」不与「在哪」共用字段**：实例记种类（如 `equip_kind`），槽位由配置表枚举；不靠 `List` / `repeated` 下标承载业务槽位顺序；纯内存展示态不写进持久化 proto。
